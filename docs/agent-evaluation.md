# Agent evaluation v1

## Separation from RDR

`skill_agent` never imports `rdr_engine`, reads a compiled tree, or calls Gemini. It sends a task and observed context to `POST /v1/resolve` and receives Markdown. `rdr_service` alone owns bundle loading, feature inference, traversal, and rendering. Changing those internals requires changing the service adapter, not the runner. Keep the public v1 contract stable; breaking public changes need a new version.

Request: `skill_id`, `task` (text), `context` (observed JSON facts), `artifact_id` (opaque snapshot ID).

Response: `markdown`, `artifact_id`, `source_fingerprint`, `resolver_revision`, opaque `metadata`, `usage` (`model_calls`, `input_tokens`, `output_tokens`, `cost_usd`; unknown values are null), and optional `capabilities` (public `name`/`description` objects, default `[]`). Backend diagnostics remain opaque. Usage must include future LLM-based selection costs.

Snapshots freeze source + compiled bundle + implementation revision. The agent only sees their public receipt. Modifying live source files does not alter an existing snapshot. Changed backend code requires a new snapshot and experiment; old runs refuse to silently resume with changed code. Snapshot preparation does not call Gemini.

## What runs

Each document/replicate has fresh attempts under the selected conditions. Full and reduced share the skill interface and differ in the active skill text; they must share the same source fingerprint. No fallback to full guidance is allowed if resolution fails.

`none` uses `NoSkillPolicy`: only the benchmark's neutral system instructions, task/public schema, execution tools, and conversation history reach the model. There is no skill catalog, skill-use instruction, skill identity, `request_skill` tool, managed skill text, or automatic refresh. No skill context is constructed for that attempt. A none-only run skips skill files, snapshot/service preparation, and resolver preflight. Manifests and summaries identify this protocol as `condition_protocols.none="skill-blind-v1"`. Earlier none results exposed a catalog and skill interface and are a different baseline.

`run_episode` performs policy → skill section → model → tools → observations until completion/budget. `SessionContext.load_skill(context, task=...)` is the shared refresh operation. A focused task uses only that request and its supplied context: the original task is not appended and prior feature values are not inherited. A refresh replaces the managed prompt section on the next call, not the audit record. The original objective, prior model-generated text and tool observations remain in history; this does not erase knowledge already seen.

`run.skill_loading="rolling"` (current pilot/DeepSeek examples and Colab default) uses `RollingSkillPolicy` before **every** model call, including when the model never calls a skill tool. Turn 0 resolves the original task. Later turns concatenate the last three assistant responses' exposed `reasoning`/`reasoning_content` (or textual `reasoning_details`) and planning content; a response with no such text falls back to its tool names/arguments. Empty windows fall back to the task. Only those three turns feed selection: no original-task prefix, previous feature values, skill text, tool outputs, labels, or full trace are appended. The existing heuristic resolver derives features, traverses the tree, and replaces the managed skill view. No selector LLM, new IR, or new tree is needed. Old topics expire from selection after three responses; old reasoning/tool history still remains in the agent conversation.

Full and reduced use the same rolling policy, catalog, tools, and automatic-mode instructions. Full receives the entire source on every call and reduced receives a fresh view on every call. `request_skill` keeps its existing signature and remains callable for these two arms, but in rolling mode returns an acknowledgement (`request_applied=false`) without invoking the resolver, inheriting context, or changing guidance. Its arguments are excluded from the fallback; ordinary reasoning/planning in that response still counts toward the three-turn window. Automatic selection does not consume an extra model call; resolver usage/latency is logged. Keyword matching remains imperfect (including negation and incidental mentions).

`run.skill_loading="model_initiated"` restores the previous behaviour: no preload or automatic refresh; `request_skill` resolves and replaces guidance normally. Old configurations omitting this option retain that behaviour. `run_episode` also retains its original default for callers supplying no policy, and `InitialSkillPolicy` remains available. Backend failures abort the attempt rather than silently keeping stale guidance.

`RDRBackend` derives catalog entries from actual IR rules and their source-section headings, excluding code-fence comments. The preflight obtains this catalog and verifies provenance; its Markdown is not itself supplied to episode models. Manifests record loading mode. Rolling `skill_request`/`skill` events include `selection.policy`, target `turn`, `source_turns` (zero-based), and `input_source`; the exact resolver input remains in `request.task`. Console output, summaries, and `inspect-skills` report `automatic_skill_refreshes` separately from model-issued calls/follow-ups. In rolling mode zero model skill calls does **not** mean no guidance. Use a new output directory; old runs cannot resume with changed code/configuration. A shorter view does not guarantee lower total usage.

## PDF benchmark protocol

- Pinned [VAREX dataset](https://huggingface.co/datasets/ibm-research/VAREX) revision `2dfc3386a4567c7d56bf1abf4d12ff42afed27b6` and [official scorer](https://github.com/udibarzi/varex-bench/tree/3cce9c18530748cfc843f38c02e2f43e0694d167/evaluation). The scorer and field exclusions are downloaded unchanged with provenance hashes.
- Flat documents: sort IDs, shuffle with seed 42, first 30 dev, remainder held out. This is **our split**, not an official train/validation/test split. The dataset's `Flat/Nested/Table` labels describe structure.
- Preparation streams only metadata columns and supports `--dev-limit N` for downloading just the first N dev PDFs. Pilot snapshots expose only those dev tasks and no held-out tasks; provenance records the selection and complete Flat population fingerprint. Full preparation retains the original split.
- `prepare --task-ids ...` downloads an exact subset of the original 30 dev IDs. `run.task_ids` selects those IDs in the specified order, overrides `limit`, and rejects IDs outside the prepared split. The diagnostic pilot uses FS5441-3E and LS-275si (six episodes, no repetitions); their prior difficult traces motivate selection, not a guarantee that a model needs skills. This is development/debugging evidence, not a held-out result.
- Each attempt gets a fresh temporary folder with the original PDF at `inputs/document.pdf` and public schema at `inputs/schema.json`. Shell commands run there using the configured venv (runner Python by default), through PowerShell on Windows or `/bin/sh` on Linux/Colab. The agent writes `answer.json`; cleanup removes the temporary folder after collection.
- Labels are excluded from prompts and public input folders; the scorer reads them after inference. A venv isolates dependencies, not filesystem/network access: arbitrary shell commands retain host user permissions and could find labels elsewhere on disk. This is a controlled, non-adversarial evaluation setup, not enforced label isolation. Credential-like environment variables are removed from tool subprocesses; this is not a security boundary. Failures produce explicit `_error` predictions and remain in the denominator. No answer repair or silent output truncation.
- Reports include normalized field exact match, perfect-document rate, per-document paired bootstrap intervals, model/selector usage, timings, and failure coverage. Unknown usage/cost is null, not zero. Setup selection is logged separately under `preflight_skill`; include it when calculating total experimental cost. Provider-neutral dollar estimates are not invented.
- This is **our raw-PDF agent protocol**, not exact direct-inference VAREX or SkillOpt reproduction. The scorer is official; the agent protocol is ours. A confidence interval alone does not establish equivalence: choose a non-inferiority margin before final held-out evaluation.

Default pilot: 5 dev PDFs × 1 replicate × 3 conditions. Main run: all held-out PDFs × 3 replicates. Defaults: temperature 0, concurrency 1, 20 model calls/10 minutes per attempt; each shell command has 60 seconds and 128 KB output. Commands are terminated on timeout/output overflow, including their active descendants. The venv adds no CPU/RAM/disk quotas. The `pdf-runtime` extra pins PDF packages; manifests capture the venv's installed package versions, Python/platform, shell, and available PDF tool paths/versions. Missing optional system tools are recorded as null. Keep the same host tools and venv for all three conditions.

Optional `run.conditions` selects a nonempty subset of `none`, `full`, `reduced` (default: all three). `["full", "reduced"]` gives 60 episodes on 30 dev documents with one attempt each. `["none"]` gives 30 skill-blind episodes; `skill` may be `{}` for that configuration. Inspection, scoring, usage summaries, and paired comparisons include only selected conditions. Use a fresh output directory for the new baseline.

## Main interfaces

| File | Interface / responsibility |
|---|---|
| `skill_agent/contracts.py` | `ResolveSkillRequest`, `ResolvedSkill`, `SkillResolver` |
| `skill_agent/resolvers.py` | `HttpSkillResolver`, `StaticSkillResolver` (full/empty) |
| `skill_agent/models.py` | `ModelClient.complete`, `OpenAICompatibleClient` |
| `skill_agent/local_models.py` | Optional `LocalTransformersClient`, FP16 Qwen server startup, two-turn tool smoke check |
| `skill_agent/runtime.py` | `Tool`, `SkillRequestPolicy`, `NoSkillPolicy`, `RollingSkillPolicy`, `planning_text`, `ModelInitiatedSkillPolicy`, `InitialSkillPolicy`, `SessionContext`, `SkillRequestTool`, `run_episode` |
| `skill_agent/benchmarks/` | `BenchmarkAdapter`, `VarexAdapter`, pinned preparation and scoring |
| `skill_agent/pdf_session.py` | `VenvPDFSession`, bounded local shell execution and venv provenance |
| `skill_agent/experiments.py` | factories, paired runs, atomic episode records, resume, reports |
| `rdr_service/backend.py` | `RDRBackend.prepare` and `.resolve`; sole RDR integration point |

Configuration factories use `module:Class` + options. Configuration files are trusted code configuration, not model-controlled input. To add a model, implement `complete(messages, tools)` returning `ModelResponse`. To add a benchmark, implement `prepare_runtime`, `tasks`, `open_session`, `score`, `system_prompt`, and `snapshot_fingerprint`. A session exposes `prompt`, `tools`, `collect`, and `close`. A scorer returns `summaries` and `document_metrics`: rows with `task_id`, `condition`, `replicate`, `metric`, `numerator`, `denominator`. This supports success-rate benchmarks as well as field-level metrics without changing the loop or paired analysis.

`OpenAICompatibleClient` optionally forwards a `provider` object for OpenRouter routing and price ceilings; other APIs keep the previous behaviour when it is omitted. For example: `{"only":["inference-net"],"allow_fallbacks":false,"require_parameters":true,"max_price":{"prompt":0.08,"completion":0.50}}`. Prices are USD per million tokens. Responses record the reported provider when available.
Provider-reported `usage.cost` is retained as `cost_usd`; providers that omit it still produce null rather than an invented dollar estimate.

## Reproducibility and limits

Run manifests record resolved configuration, task IDs, package/code/Git revisions, host and venv dependency versions, dataset fingerprints, source fingerprint, and service receipt. Episode records contain exact requests/responses, tool calls, skill views, provenance and usage. Filenames use `<document>_<condition>_<hash>.json`; the original document/condition/repetition hash preserves uniqueness, and unsafe ID characters are percent-encoded. Resume also recognizes legacy hash filenames. `rename-episodes` converts saved names without rewriting records or bypassing integrity checks. Resume is at completed-episode boundaries and refuses changed configuration/artifacts; it does not retry already-recorded failures. Use a new output directory for a new experiment, including when switching from the previous Docker runtime. A crash may leave `.running`: first ensure no runner is active, then remove that exact run's lock before resuming. Local service binds only to loopback; expose it remotely only behind proper authentication/TLS.

The current PDF source is an existing supplied local snapshot with restrictive upstream provenance; this work does not clear those terms or fetch missing supporting guides. `FORMS.md`, `REFERENCE.md`, and upstream scripts are absent. Treat it as an incomplete skill snapshot, not the full upstream package. The filename is normalized to `initial.md` for Linux compatibility, without content changes.

Current PDF selection still uses deterministic heuristics for case building. On the `MCRDR-testing` branch the service resolves through the multiple-classification (MCRDR) engine: a flat tree with an unconditional general-guidance rule and one rule per condition, no rule limit, and the fragments of every terminal conclusion rendered. Identical extraction requests can yield the same view even for different documents; different task contexts can select different guidance. An OCR-only request selects the OCR branch without forcing general extraction fragments; explicitly asking to extract text and use OCR selects both. General instructions and structural dependencies still apply. The harness does not fix selection quality.

## MCRDR runs

The MCRDR bundles are compiled from the same `ir.json` as the single-classification (SCRDR) bundles, and every rendered combination of the PDF and ALFWorld skills was verified byte-identical between the two engines. For the same resolver input, the reduced arm therefore receives exactly the same Markdown as in the SCRDR runs. Differences between MCRDR and SCRDR results come from model nondeterminism and from rolling-selection inputs (which depend on the model's own reasoning), not from different guidance for the same input. The none and full arms do not touch the engine.

`resolve` metadata (opaque to the runner, recorded in episodes) now contains `engine` (`"mcrdr"`), `engine_schema_version`, `case`, `fragment_ids`, `terminal_ids` (nodes whose conclusions were rendered) and `trace` (every evaluated node with `node_id`, `matched` and `depth`). The SCRDR `path` field no longer exists. `case` and `fragment_ids` keep their meaning, so selected views can be compared across engines.

Snapshot IDs include the engine and service code revision, so MCRDR snapshots never collide with SCRDR snapshots, and SCRDR runs refuse to resume against MCRDR code. `prepare` rejects bundles compiled for the single-classification engine (artifact schema 1) before copying anything. The `examples/agent/varex.mcrdr.*.json` configurations match their originals except for `skill.receipt` (`experiments/pdf-snapshot-mcrdr.json`) and an `experiments/mcrdr-*` output directory, so results from the two engines are never mixed.

Implemented: service boundary/snapshots, generic loop, optional model-initiated loading/refresh with a public capability catalog, OpenAI-compatible model adapter, three arms, local venv PDF/data/scorer adapters, exact-ID pilots, accounting, resume, and request inspection. Hosted experiments with automatic initial loading have run on Colab. A limited Qwen3.7 Flash check on FS5441-3E and LS-275si elicited one model-issued request in all six attempts after strengthening the shared workflow instructions and listing the skill tool first. Initial request hashes (messages plus tools) matched across all three conditions for each document. These checks stopped at six model calls per attempt and do not establish task accuracy; live follow-up requests and full-budget/held-out evaluation remain pending. No trace-based update integration is included.

Latest reduced-only repeat with the explicit two-failure instruction: LS-275si made one request and FS5441-3E's extraction/rotation/encryption task made none. Neither made a follow-up before the diagnostic token allowance stopped the attempt. Prompt wording alone has not demonstrated reliable refresh behaviour; these are not accuracy results.

DeepSeek V4.1 Flash 1017 diagnostic (2026-10-18, Windows, InferenceNet): with the same prompt/tools and no automatic loading, FS5441-3E voluntarily requested extraction guidance and then a different rotation/security view; its output PDF passed rotation, encryption, password, and page-count checks. LS-275si requested extraction guidance but ended with `finish_reason="length"` at the 2,048-token response cap, before writing an answer. Both used seven calls; total reported cost was $0.003615. These two reduced-only diagnostics do not establish an accuracy/cost advantage or Colab compatibility. The 30-document run has not started.

Authorized LS-275si-only repeat with an 8,192-token response cap: five model responses and one extraction request, then the private diagnostic guard stopped the sixth call after a 58,453-character form-field dump. Actual usage was 39,312 tokens; the guard added an 81,652-byte serialized prompt plus output/safety reservations to prior usage, exceeding its conservative 120,000 allowance. No response hit the new output cap and no answer was collected. Rerun cost: $0.002848; combined DeepSeek diagnostics: $0.006463. This byte-based diagnostic guard is not used by the standard Colab experiment runner. No further rerun or 30-document run was launched.

Usage: 106,598 input + 3,656 output tokens; reported cost $0.005094. No automatic loading, pre-inspection, reminder, or history truncation was added. The private diagnostic retained provider price limits and a separate conservative dollar ceiling. Total reported spending across all DeepSeek diagnostics was $0.011557. The earlier FS5441-3E diagnostic scored 3/3 extraction fields and passed its additional PDF checks; these are selected debugging cases, not a matched accuracy/cost comparison. A 30-document Colab configuration can now use the same provider settings and 8,192-token cap across all three conditions; it has not been executed.
